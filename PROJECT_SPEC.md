You are helping me bootstrap a professional Master's thesis engineering project called **EdgeGuard IoT**.

## Project goal

EdgeGuard IoT is an Edge AI-based anomaly detection and security monitoring system for a Smart Home IoT environment.

The project evolves an existing engineering thesis prototype.

The previous system consisted of:

* Raspberry Pi 3
* Arduino Mega 2560
* Flask web application
* USB serial communication between Raspberry Pi and Arduino
* approximately 9 LEDs representing room lighting
* 4 servo motors controlling doors, gates and garage elements
* 3 MQ-9 gas sensors
* fans automatically activated when gas concentration exceeded a predefined threshold

The Master's thesis version will remove the Arduino Mega from the main architecture and replace it with a distributed ESP32-based IoT architecture.

The exact final number of ESP32 nodes is intentionally not fixed yet.

The architecture must support:

* one ESP32 for a minimal prototype
* two ESP32 nodes for a distributed MVP
* three or more ESP32 nodes without requiring a major architectural redesign

The expected physical implementation will most likely use 2 or 3 ESP32 development boards.

## Main research objective

The purpose of the Master's thesis is to investigate whether lightweight machine learning algorithms can effectively detect anomalous behaviour and selected security-related anomalies in a distributed Smart Home IoT environment while performing inference on Edge hardware.

The research should compare selected anomaly detection approaches in terms of:

* Precision
* Recall
* F1-score
* False Positive Rate
* inference latency
* CPU usage
* RAM usage
* model size

Initial candidate algorithms:

* Isolation Forest
* One-Class SVM
* Local Outlier Factor
* Random Forest as a supervised baseline
* optional lightweight Autoencoder

Do NOT introduce unnecessary deep learning complexity during the initial implementation.

## Simulator

A simulator is a critical part of the project.

The simulator must allow software and ML development without requiring continuous access to the physical Smart Home model.

It should emulate multiple independent IoT devices.

Example simulated topology:

* esp32_node_01
* esp32_node_02
* esp32_node_03
* virtual_node_04
* virtual_node_05
* etc.

The exact number of simulated devices should be configurable.

The simulator should publish telemetry using the same MQTT schema as real ESP32 devices.

### Normal mode

Simulate realistic normal behaviour:

* MQ gas sensor values
* light state
* fan state
* door/gate state
* actuator activity
* MQTT frequency
* signal strength
* uptime
* heartbeat

### Anomaly mode

Support controlled scenarios such as:

* gas spike
* sensor freeze
* sensor noise
* sensor drift
* MQTT flood
* command flood
* repeated gate operations
* device offline
* actuator mismatch
* spoofed sensor measurement
* abnormal telemetry frequency

Simulation must be deterministic when a random seed is supplied.

## Operational anomalies

Examples:

* abnormal MQ-9 readings
* sensor stuck at a constant value
* abrupt impossible sensor changes
* fan not activating during high gas readings
* actuator not responding
* excessive actuator activity
* ESP32 node going offline

## Security-related anomalies

Examples:

* excessive MQTT traffic
* abnormal command frequency
* repeated control commands
* spoofed sensor values
* unexpected device behaviour
* device publishing data at an abnormal frequency
* device attempting to behave like another IoT node

Do NOT create destructive, offensive or Internet-facing attack functionality.

All security scenarios must remain safe, controlled and local to the laboratory environment.

## ESP32 firmware

Use:

* C++
* PlatformIO
* Arduino Framework initially

Firmware architecture should contain modules/interfaces for:

* Wi-Fi
* MQTT
* telemetry
* heartbeat
* command handling
* MQ-9 sensors
* LED outputs
* servo control
* fan control

Exact GPIO mappings will be defined later.

Create a clearly isolated hardware configuration file.

Important electrical constraint:

ESP32 GPIO uses 3.3 V logic.

Never assume that a sensor previously connected to Arduino Mega can be directly connected to ESP32.

MQ-9 analog outputs and other 5 V devices may require voltage dividers, level shifting or separate driver circuitry.

Servo motors and fans must not be powered directly from ESP32 GPIO pins.
